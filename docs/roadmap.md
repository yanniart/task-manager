# 차후 계획 (로드맵)

- 문서 버전: v0.1 · 2026-11-11
- 관련 문서: [PRD](PRD.md) · [TRD](TRD.md) · [개발로그](dev-log.md) · [기술로그](tech-log.md)

v0.9까지 PRD에서 **범위 밖**으로 두었던 기능 네 가지를 앞으로 어떻게 만들지 정리한 문서예요. 아직 만들기로 **확정한 것은 아니고**, 시작할 때 이 문서를 바탕으로 PRD에 기능 번호(F19~)를 붙이고 TRD·기술로그를 고쳐요.

| 번호 | 기능 | 서버 필요 | 크기 | 추천 순서 |
|---|---|---|---|---|
| R0 | (준비) 지난 기록 남기기 | 아니요 | 중 | 1 |
| R1 | 지난 기록 통계 | 아니요 | 중 | 2 |
| R2 | 달력 보기 | 아니요 | 중 | 3 |
| R3 | 기기 간 동기화 | **예** | 대 | 4 |
| R4 | 알림 | **예** | 대 | 5 |

## 바로 시작하기

다음 세션에서 이어서 할 때 이 순서로 하면 돼요.

1. 클로드 코드를 `C:\dev\task-manager`에서 열어요(루트의 `CLAUDE.md`를 먼저 읽어요).
2. 이렇게 말해요: **"docs/roadmap.md의 R0부터 시작하자"** (다른 것: [prompts.md의 "차후 계획 시작하기"](prompts.md#차후-계획-시작하기))
3. 클로드가 그 절의 **"정해야 할 것"**을 먼저 물어봐요. R0이면:
   - 자세한 완료 기록을 얼마나 둘지 (제안: 1년)
   - "기록 지우기"를 할 일 데이터 지우기와 따로 둘지
   - 내보내기에 기록을 넣을지 (제안: 넣음)
4. 정해지면 PRD에 기능 번호(F19~), TRD에 설계, 기술로그 TL-026을 쓰고, 테스트와 함께 만들어요.
5. 끝나면 "커밋하고 배포해 줘" → 배포 주소 확인까지.

시작 전 상태: PRD v0.9 · TRD v0.8 · 다음 기술로그 번호 TL-026 · 저장 형식 `version: 1` · 서비스 워커 캐시 `v7` · 확인 core 78 / store 23 / 브라우저 185 / 배포 9 모두 통과 (2026-11-11).

**순서를 이렇게 추천하는 이유**

- R1·R2는 서버 없이 지금 원칙(순수 웹, 브라우저 저장) 안에서 만들 수 있고, 둘 다 **R0(지난 기록)**만 있으면 돼요. R0을 먼저 넣으면 그날부터 기록이 쌓이니, 통계 화면을 만들 때쯤엔 볼 데이터가 생겨 있어요.
- R3·R4는 **서버가 있어야** 해요. 그래서 TRD 1장 "순수 웹 기술만", TRD 7장 "외부로 데이터를 보내는 코드는 없어요", PRD 2장 "서버·로그인 없음"을 바꾸는 결정이 먼저 필요해요.
- R4(알림)는 앱이 닫혀 있을 때도 울리려면 **푸시를 보낼 서버**가 필요해서, R3에서 만든 서버를 같이 쓰는 것이 가장 적게 들어요.

## R0. 지난 기록 남기기 (준비 작업)

### 목표

날짜가 바뀔 때마다 **그날의 요약**을 남기고, 완료한 할 일의 **기록**을 할 일 목록과 따로 보관해서, 사용자가 할 일을 지워도 통계·달력에는 남게 해요.

### 설계 초안

- 저장 형식 `version: 2` — 이 앱의 **첫 마이그레이션**이에요(`storage.js`의 `migrations[1]`). 예전 데이터는 지금 남아 있는 완료 항목으로 기록을 미리 채워요(있는 만큼만).
- `history.days`: 날짜별 요약. 날짜 처리(`runRollover`)가 지난 날짜를 정리하기 **직전에** 그날 값을 계산해서 넣어요.

  ```js
  history: {
    days: {
      "2026-11-10": {
        total: 12, done: 9,           // 그날 오늘 목록에 있던 할 일 / 그중 끝낸 것
        carriedOut: 2,                // 다음 날로 넘어간 것
        byCategory: { work: { total: 5, done: 4 }, personal: {…}, study: {…} },
        rules: { "<ruleId>": true }   // 그날 반복 일정을 했는지 (true/false)
      }
    },
    done: [                           // 완료 기록 (자세한 것, 기간 제한)
      { id, text, category, date, completedAt, ruleId, carriedFrom }
    ]
  }
  ```

- 완료 기록(`history.done`)은 **완료로 바꿀 때** 넣고, 완료를 취소하면 빼요. 할 일을 지워도 기록은 남아요.
- 용량: 요약은 하루 0.3KB 정도라 몇 년치도 괜찮아요. 자세한 기록은 하루 20개면 1년에 약 1~1.5MB라서 **최근 1년만** 두고, 그보다 오래된 건 요약만 남기는 걸 제안해요.
- 설정에 "기록 남기기" 끄기와 "기록 지우기"를 둬요(개인 기록이라).

### 정해야 할 것

- [ ] 자세한 기록을 얼마나 둘지 (제안: 1년)
- [ ] "기록 지우기"를 할 일 데이터 지우기와 따로 둘지
- [ ] 내보내기(F15)에 기록을 넣을지 (제안: 넣음)

### 완료 기준

- 날짜를 넘기며(`?today`) 쓴 뒤 요약 값이 손으로 센 것과 같음
- 완료 항목을 모두 지워도 그날 요약·완료 기록은 남음
- `version: 1` 데이터를 불러오면 `version: 2`로 바뀌고 할 일은 그대로
- 같은 날 여러 번 날짜 처리를 해도 요약이 한 번만 쌓임 (멱등성, TRD 5.2)

## R1. 지난 기록 통계

### 사용자 이야기

- 지난 한 주·한 달 동안 얼마나 해냈는지 보고 싶어요.
- 어떤 카테고리를 자주 미루는지 알고 싶어요.
- 매일 하기로 한 반복 일정을 며칠 연속 지켰는지 보고 싶어요.

### 화면 초안

- 헤더 ⋯ 더보기 또는 새 📊 버튼 → **기록** 화면(반복 일정 관리처럼 전체 화면)
- 기간 고르기: 최근 7일 / 30일 / 이번 달
- 보여줄 것
  - 날짜별 완료율 **막대**(가로 7개 또는 30개)
  - 카테고리별 끝낸 수·완료율
  - **연속 기록**: 할 일을 모두 끝낸 날이 며칠 이어졌는지
  - 반복 일정별 달성률 ("영단어 30개 — 최근 30일 중 24일")
  - 가장 자주 이월된 할 일 상위 5개
- 그래프는 라이브러리 없이 CSS·SVG로 그려요(TRD 1장). 숫자도 함께 써서 색만으로 읽지 않게(접근성). 라이트·다크 대비 기준(TRD 6장)을 그대로 지켜요.

### 정해야 할 것

- [ ] 들어가는 곳: 더보기 안 / 헤더 새 버튼 / 진행률 영역을 눌러서
- [ ] "하루를 다 끝냄"의 기준: 그날 할 일 100% / 미완료가 0개 / 할 일이 1개 이상 있을 때만 셀지

### 완료 기준

- 기록이 0일·1일·30일 이상일 때 모두 화면이 깨지지 않음
- 300일치 요약에서도 화면을 여는 데 100ms 안 (CPU 4배 느리게, TRD 5.14 방식)
- 확인 스크립트에 통계 단계를 추가(`tests/e2e/steps/`), 계산은 core 함수로 만들어 core 테스트에 추가

## R2. 달력 보기

### 사용자 이야기

- 한 달을 한눈에 보며 잘한 날·못한 날을 알고 싶어요.
- 지난 어떤 날에 무엇을 했는지 다시 보고 싶어요.
- 다음 주에 어떤 반복 일정이 잡혀 있는지 미리 보고 싶어요.

### 화면 초안

- **월 달력**: 날짜 칸마다 완료율을 옅은 색 단계로(R0의 요약). 색만으로 구분하지 않게 칸 안에 작은 숫자도.
- 지난 날짜를 누르면 **그날 기록**: 끝낸 할 일(완료 기록), 넘어간 개수, 카테고리별 수
- 오늘은 지금의 오늘 목록으로 이동
- 앞으로의 날짜를 누르면 그날 생길 **반복 일정 미리 보기**(`recurrence.matches`로 계산, 저장은 안 함)
- 휴대폰 360px에서 7칸이 각 44px 이상 되게(지금 요일 칸과 같은 조건, TL-016)

### 정해야 할 것 (중요)

- [ ] **앞으로의 날짜에 할 일을 미리 넣을 수 있게 할지.** 지금 앱은 "항상 오늘"(PRD 4장)이라, 넣게 하면
  - 할 일의 `date`가 미래일 수 있게 되고, 날짜 처리·진행률·검색·정렬 규칙을 모두 다시 봐야 해요
  - 이월과의 관계(미래 할 일은 그날이 되면 나타남)를 정해야 해요
  - → 제안: 처음에는 **보기만**(기록 + 반복 미리 보기), 미래 할 일은 다음 단계로 따로 결정
- [ ] 주 시작 요일 (월요일 / 일요일)

### 완료 기준

- 31일·30일·28/29일 달, 1일이 일요일·토요일인 달에서 칸이 맞음 (core 테스트)
- 시간대가 달라도 날짜 칸이 밀리지 않음 (`node tests/run-core.mjs --tz=…`로 확인, TL-005·TL-024)
- 기록이 없는 날은 빈칸으로, 오류 없이

## R3. 기기 간 동기화

### 사용자 이야기

- 휴대폰에서 적은 할 일을 PC에서도 보고 싶어요.
- 휴대폰을 바꾸거나 브라우저 데이터를 지워도 할 일을 잃고 싶지 않아요.

### 꼭 필요한 결정 (원칙을 바꿔요)

- 서버와 **계정(로그인)**이 생겨요 → PRD 2장 "로그인·서버 없음", TRD 7장 "외부로 보내는 코드 없음"을 바꿔요.
- 데이터가 기기 밖으로 나가요 → 동기화는 **켜는 사람만**(기본은 꺼짐), 켤 때 무엇이 어디로 가는지 알려 줘요.
- 오프라인에서도 지금처럼 동작해야 해요(PWA). 브라우저 저장소가 **기본**이고, 서버는 **복사본**이에요.

### 방법 비교

| 방법 | 좋은 점 | 아쉬운 점 |
|---|---|---|
| **A. 서버형 백엔드(예: Supabase)** — 로그인 + 데이터베이스 | 여러 기기 실시간에 가까운 동기화, 무료 범위로 개인 사용 충분, 행 단위 권한(RLS)으로 내 데이터만 | 계정·서버 관리, 원칙 변경 폭이 큼 |
| B. 내 클라우드 파일(예: Google Drive 앱 전용 폴더) | 내 계정에 저장, 운영할 서버 없음 | OAuth 설정, 동시 수정 충돌을 파일 단위로 처리, 브라우저 지원 제약 |
| C. 지금처럼 내보내기·가져오기 + 편의 기능(예: QR로 옮기기) | 원칙 그대로, 가장 단순 | 자동이 아니고 합치기가 안 됨 |

- 제안: **A**. 단, 라이브러리 없음 원칙(TRD 1장)을 지키려면 공식 SDK 대신 REST API를 `fetch`로 직접 불러요. 로그인은 이메일 링크(매직 링크)로 비밀번호 없이.

### 데이터 모델에 필요한 것

- 할 일·반복 일정마다 `updatedAt`(고친 시각)과 `deleted`(지웠다는 표시, "묘비") — 지금은 휴지통에 30일만 있어서, 오래 꺼져 있던 기기가 지운 할 일을 되살릴 수 있어요.
- 충돌 규칙: 항목마다 **나중에 고친 쪽이 이김**. 순서(`order`)는 합친 뒤 `renumber`로 다시 매겨요(TL-011).
- 설정(필터·정렬·화면 모드)은 기기마다 따로 둘지 같이 둘지 정해야 해요(제안: 화면 모드·정렬은 기기마다, 자동 분류 키워드는 같이).
- 이미 id가 `crypto.randomUUID()` 기반이라 기기끼리 겹치지 않아요(TL-010) — 그대로 쓸 수 있어요.

### 단계 초안

1. 데이터 모델: `updatedAt`·`deleted` 추가(저장 형식 버전 올림), 기존 기능 테스트가 모두 그대로 통과
2. 서버: 테이블·권한 규칙, 로그인
3. 동기화: 앱을 열 때·다시 보일 때·고친 뒤 잠시 뒤(디바운스) 보내고 받기, 오프라인이면 미뤄 두기
4. 화면: 더보기 → 동기화 켜기/끄기, 마지막 동기화 시각, 로그아웃, "이 기기 데이터만 남기기"
5. 확인: 두 기기 흉내(브라우저 프로필 두 개)로 동시 수정·삭제·오프라인 후 합치기

### 정해야 할 것

- [ ] 방법 A / B / C
- [ ] 비용 상한(무료 범위만)
- [ ] 처음 켤 때 이미 두 기기에 다른 데이터가 있으면: 합치기 / 한쪽으로 바꾸기
- [ ] 계정을 지우면 서버 데이터도 지우기(개인정보)

### 위험

- 저장소 두 곳(브라우저·서버)이 어긋나는 문제는 테스트하기 어려워요 → 합치기 로직은 순수 함수(core)로 만들어 경우의 수를 테스트로 많이 돌려요.
- 공개 저장소라서 서버 키는 **공개용 키만** 앱에 넣고, 비밀 키는 절대 넣지 않아요.

### 지난 결정

알림은 v0.2에서 넣었다가 v0.3에서 **뺐어요**([TL-003](tech-log.md#tl-003) → [TL-009](tech-log.md#tl-009)). 이유:

- 서버 없이는 **앱이 닫혀 있을 때 알림을 보낼 수 없어요**(브라우저가 예약 알림을 지원하지 않음, Notification Triggers는 중단됨).
- iPhone은 **홈 화면에 추가한 앱**에서만(iOS 16.4 이상) 알림을 받을 수 있어요.
- 이월된 할 일의 알림이 다시 울리지 않는 문제가 있었어요.

### 다시 넣는다면

- **Web Push + 서버**: 휴대폰마다 푸시 구독 정보를 서버에 저장하고, 서버가 정해진 시각에 푸시를 보내요(예: Supabase의 예약 작업 + 함수). 서비스 워커가 받아서 알림을 띄워요.
- R3의 서버·계정을 같이 써요 → **R3 다음**에.
- 알림 종류 제안
  - 할 일에 시각 지정 ("15:00 회의 준비")
  - 반복 일정에 시각 지정 ("매일 21:00 영단어")
  - 하루 요약 ("오늘 할 일 3개가 남았어요" — 정한 시각에 한 번)
- 데이터: `todo.remindAt`, `rule.remindTime`. **이월될 때 알림을 어떻게 할지**(같은 시각에 다음 날 다시 / 끄기)를 꼭 정해요.
- 권한: 처음부터 묻지 않고, 사용자가 알림을 처음 켤 때 물어봐요. 거절했으면 다시 켜는 방법을 안내해요.

### 정해야 할 것

- [ ] 알림 종류(할 일 시각 / 반복 시각 / 하루 요약) 중 무엇부터
- [ ] 이월된 할 일의 알림 규칙
- [ ] 방해 금지 시간(예: 밤 11시~아침 7시)

### 위험

- iPhone은 홈 화면에 추가하지 않으면 알림이 오지 않아요 → 켤 때 안내가 필요해요.
- 서버 예약 작업이 늦거나 실패하면 알림이 늦어요 → "정확한 시각 보장 없음"을 안내.
- 푸시 키(VAPID)의 비밀 키는 서버에만.

## 시작할 때 할 일 (모든 기능 공통)

1. 이 문서의 해당 부분을 바탕으로 **PRD에 기능 번호**(F19~)를 붙이고 "정해야 할 것"을 사용자와 정해요.
2. TRD에 데이터 모델·로직을 쓰고, 원칙을 바꾸는 결정(서버, 외부 요청)은 **기술로그에 새 TL**로 남겨요.
3. 저장 형식이 바뀌면 `version`을 올리고 `storage.js`에 마이그레이션 + 예전 데이터로 테스트.
4. 확인 스크립트(`tests/`)를 먼저 또는 함께 만들고, 기존 확인(core·store·브라우저 185개)이 그대로 통과하는지 봐요.
5. 앱 파일을 바꾸면 `sw.js`의 `CACHE_VERSION`을 올리고, 배포 후 `deployed` 확인(TRD 8장).

앞으로 쓸 프롬프트는 [prompts.md](prompts.md)의 "차후 계획 시작하기"에 있어요.
